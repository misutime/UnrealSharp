## 1. UnrealSharp 的执行模型（理解本 bug 的前提）

### 1.1 两个运行时并排跑

一个跑着 UnrealSharp 的编辑器进程里同时存在两套运行时：

- **UE（C++）**：拥有 `UObject` 世界——反射系统（`UClass`/`UStruct`/`UFunction`/`FProperty`）、对象数组与哈希表（`GUObjectArray`/`FUObjectHashTables`）、GC、线程管理。
- **.NET**：由插件通过 `hostfxr` 启动，入口程序集是 `UnrealSharp.Plugins.dll`；`UnrealSharp.dll`（引擎绑定所在的核心托管程序集）、`UnrealSharp.Editor.dll`、以及 `Script/` 下的用户工程各自是独立程序集，经 `AssemblyLoadContext`（每个插件一个 ALC）加载。**热重载 = 卸载旧 ALC、编译并加载新 ALC、重新登记类型**。

两套运行时之间的**互操作全部由生成的桥接代码显式完成**（没有自动的 P/Invoke 映射）：

- **C# → C++**：`Bind_*` 静态类里的函数指针，由原生在启动时填充（`[NativeCallbacks]`），例如 `Bind_UCoreUObject.CallGetNativeField(...)`。
- **C++ → C#**：`[UnmanagedCallersOnly]` 回调（如 `UnmanagedCallbacks.InvokeManagedMethod`），配合 `GCHandle` 把托管对象/委托固定住；原生拿句柄调用，调用结束释放——`FCSManagedDelegate::Invoke(..., bool bDispose = true)` 默认释放（`CSManagedDelegate.h:17-18`、`CSManagedDelegate.cpp:29-34`），释放链最终到托管 `UnmanagedCallbacks.Dispose` → `GCHandleUtilities.Free` → `GCHandle.Free()`。

### 1.2 类型系统怎么对接

C# 类型必须**在引擎反射系统中登记**才能被 UE 使用。两个方向：

- **引擎类型 → C#**：`UnrealSharp.csproj` 编译 `Intermediate/UnrealSharp/UHT/$(UETargetType)/**` 下生成的**绑定类**（如 `AActor` 的绑定）。这些是普通 C# 类，其属性偏移/函数指针在运行期向原生查询并缓存。
- **C# 类型 → 引擎**：`[UClass]`/`[UStruct]` 的元数据被 glue 生成器序列化成 JSON，原生 `UCSManagedAssembly::RegisterManagedType` → 类型编译器生成真正的 `UClass`/`UScriptStruct`/`UFunction`，由 `FCSManagedTypeDefinition` 持有。

**登记的单位是程序集**：原生侧用 `UCSManagedAssembly` 这个 `UObject` 表示"某个托管 dll 已登记"，存于 `UCSManager::Assemblies`（`TMap<FName, TObjectPtr<UCSManagedAssembly>>`）。

### 1.3 绑定类的静态构造（关键机制）

生成的绑定类在**类型初始化器**里解析原生类型指针：

```csharp
// Intermediate/UnrealSharp/UHT/Editor/UnrealSharpEditor/CSEditorBlueprintFunctionLibrary.generated.cs:16-24
static readonly IntPtr NativeClassPtr =
    UnrealSharp.Core.NativeReflectionHelper.GetNativeField(typeof(UCSEditorBlueprintFunctionLibrary), "UCSEditorBlueprintFunctionLibrary");
static UCSEditorBlueprintFunctionLibrary()
{
    AddAssemblyDependencies_NativeFunction = Bind_UClass.CallGetNativeFunctionFromClassAndName(NativeClassPtr, "AddAssemblyDependencies");
    ...
}
```

含义：**第一次触碰某个绑定类**（访问其静态成员、构造实例、调用其静态方法）就会跑一次原生的"把该类型的字段指针给我"。

### 1.4 懒加载：为什么"查个指针"会创建 `UObject`

修复前，原生侧该调用的实现：

```cpp
// Bind_UCoreUObject::GetType / GetNativeField
UCSManagedAssembly* Assembly = UCSManager::Get().FindOrLoadAssembly(InAssemblyName);
```

```cpp
// CSManager.h:51-59
UCSManagedAssembly* FindOrLoadAssembly(FName AssemblyName, bool bIsCollectible = false)
{
    if (UCSManagedAssembly* Assembly = FindAssembly(AssemblyName)) return Assembly;
    return LoadUserAssemblyByName(AssemblyName, bIsCollectible);   // ← 未命中就"加载"
}
```

```cpp
// CSManager.cpp:163-220（LoadAssemblyByPath 摘录）
if (UCSManagedAssembly* ExistingAssembly = FindAssembly(*AssemblyName)) { ... }
else
{
    Assembly = NewObject<UCSManagedAssembly>(this, *AssemblyName);   // ← 创建 UObject
    Assembly->Initialize(AssemblyPath, bIsCollectible);
    Assemblies.Add(Assembly->GetFName(), Assembly);
}
```

启动时的"加载清单"（`UserCode.LoadOrder.json` / `GlueCode.LoadOrder.json`）只列用户侧程序集；本机实际内容为：

```
UserCode.LoadOrder.json : ["TheBattleWorld.RuntimeGlue", "TheBattleWorldGameScripts"]
GlueCode.LoadOrder.json : ["TheBattleWorld"]
```

**核心绑定程序集 `UnrealSharp` 不在清单里**：它在 .NET 侧当然已被加载（否则托管代码跑不起来），但在 `UCSManager::Assemblies` 中**没有登记项**。于是"第一次触碰任意引擎绑定类"等价于"懒加载 `UnrealSharp` 程序集" = **建一个 `UCSManagedAssembly` UObject**。

崩溃转储中的直接证据：

```
Unable to create new object: CSManagedAssembly /Engine/Transient.CSManager.UnrealSharp.
Creating UObjects while Collecting Garbage is not allowed!
```

### 1.5 线程模型与 `async`

**引擎侧约定**：`UObject` 的创建/修改/生命周期操作属于游戏线程；GC 在游戏线程上同步执行，并在可达性分析期间**锁住对象哈希表**：

```cpp
// UObjectGlobals.cpp:3484（StaticAllocateObject 内）
checkf(!IsGarbageCollectingAndLockingUObjectHashTables(),
       TEXT("Unable to create new object: %s %s.%s. Creating UObjects while Collecting Garbage is not allowed!"), ...);
```

该标志由 `FGCHashTableScopeLock` 在其构造/析构之间置位（`GarbageCollection.cpp:137-154`），即只在 `CollectGarbage` 内 `LockUObjectHashTables()`…`UnlockUObjectHashTables()`（`GarbageCollection.cpp:5787 / 5893`）之间为真。**这是一句裸 `checkf`，不返回：命中即 fatal。**

**.NET 侧**：`await` 续体回到哪条线程，取决于 await 那一刻的 `SynchronizationContext.Current`（`[ThreadStatic]`）或 `TaskScheduler.Current`；**没有上下文时，续体由"完成任务的那条线程"执行**。UnrealSharp **不安装全局游戏线程上下文**；`UnrealSynchronizationContext.ConfigureWithUnrealContext()` 是**逐点 opt-in**（且其构造要求有效 world：`UnrealSynchronizationContext.cs:240-248`，`Post` 在 world 失效时静默丢弃：`:276-281`）。

因此插件内部有条纪律：**任何 `await` 之后还要碰引擎的 C# 代码，必须显式回到游戏线程**。运行时的异步资源加载（`AsyncLoadUtilities` 等）确实都走了 `ConfigureWithUnrealContext()`；**唯独编辑器侧的这个入口没有**。

### 1.6 编辑器启动时序（本 bug 的发生场景）

1. `UCSHotReloadSubsystem::Initialize()`（Editor 模块）通过托管回调指针调用 `SolutionManager.LoadSolutionAsync(slnPath, callbackPtr)`（`CSHotReloadSubsystem.cpp:39`）。
2. `LoadSolutionAsync` 是 `async void`（`SolutionManager.cs:52`），内部用 `MSBuildWorkspace`（Roslyn）解析 `Script/ManagedTheBattleWorld.sln` 并运行 glue 生成器——**纯托管工作**；首个 `await` 之后续体在**线程池**上继续（探针实测 `IsInGameThread=false`，线程 70396）。
3. 与此同时，游戏线程在加载启动模板地图（`OpenWorld.umap`），`UWorld::CleanupWorld` 触发一次 GC，`Compacting FUObjectHashTables`。

## 2. 什么算"碰引擎"

C# 与 C++ 之间没有隐式互操作，因此"碰引擎"可以精确归为五类；命中任意一类即受线程约束：

| 类别 | 具体 | 例子 / 依据 |
|---|---|---|
| **(a) 读写引擎对象内存** | 访问 `[UProperty]` 属性（走缓存的 `FProperty` 偏移）、读写引擎结构体/容器 | `actor.ActorLocation`、`Health += 1`。**没有 `[UProperty]` 标注的普通 C# 字段是纯托管内存，不碰引擎**——这是最实用的区分线 |
| **(b) 调用引擎/蓝图函数** | 把参数 marshal 到原生栈缓冲（`stackalloc byte[ParamsSize]` + 偏移）后用函数指针调原生 | `SetActorLocation`、`UGameplayStatics.*`、蓝图库函数 |
| **(c) 创建/销毁对象** | `NewObject<T>`、`SpawnActor`、`AddComponent*`、`CreateWidget`、`Destroy` | — |
| **(d) 元操作** | 类型注册（`RegisterManagedType` → 编译 `UClass`/`UStruct`）、解析原生字段指针、**懒加载程序集**、`UStruct` 原生内存分配 | 本 bug 命中这一类的"懒加载"分支 |
| **(e) 与引擎 GC 的对接** | 句柄表（`GCHandle`/`FGCHandle`）、对象包装建立、`IsValid`、`TStrongObjectPtr`、`AddReferencedObjects` 路径 | — |

**判定三问**：① 最终会不会走 `Bind_*`/访问 `NativeObject`/解析 `NativeReflectionHelper`？② 会不会建对象、注册类型、加载程序集、动句柄？③ 读写的是 `[UProperty]`/引擎类型还是普通 C# 成员？—— 翻一眼生成的 `.generated.cs`：出现 `Bind_...Call`、`NativeClassPtr`、`paramsBuffer` 就是碰引擎。

**C# 类型与原生 C++ 类型在线程规则上完全等价**：`[UClass]` 注册后本身就"变成"引擎的 `UClass`，实例就是引擎 `UObject`（分配在引擎对象数组里，由引擎 GC 管生死），C# 侧只是持原生指针的 wrapper，两者一对一绑定。区别只有一条：C# 类型多了"注册/编译成 UClass"这一步，而**这一步本身也是引擎操作（(d) 类）**。

**"只是读"也不安全**：引擎 GC 在游戏线程上销毁对象、改动哈希表；池线程同时读一个 `UObject` 的属性是 data race，可能读到正在回收的对象（UAF），而不是"读到旧值"这么温和。UE 的常规做法是游戏线程把数据拷贝出来再交给其它线程。

**因此纪律不是"少碰引擎"（玩法代码必须碰），而是"碰引擎必须在游戏线程上"**。引擎事件回调（`BeginPlay`/`Tick`/`EndPlay`、蓝图事件、输入、`SetTimer`、GT 上的委托广播、UMG 回调）天然满足；破掉它的只有主动把执行流挪走：未回 GT 的 `await` 续体、`Task.Run`、计时器、第三方库回调、.NET 终结器线程。

## 3. Bug 的原因与机制

### 3.1 精确调用链（崩溃转储中的托管栈）

```
SolutionManager.LoadSolutionAsync                        (SolutionManager.cs:66)   ← 线程池
  → SolutionManager.BuildProjectDependencyMap            (SolutionManager.cs:82)
    → UCSEditorBlueprintFunctionLibrary.AddAssemblyDependencies(...)              ← 首次触碰该绑定类
      → 静态构造 → NativeReflectionHelper.GetNativeField(typeof(T))
        → Bind_UCoreUObject::GetNativeField
          → UCSManager::FindOrLoadAssembly("UnrealSharp")            → miss
            → LoadUserAssemblyByName → LoadAssemblyByPath
              → NewObject<UCSManagedAssembly>(...)                    ← 创建 UObject
                → checkf(!IsGarbageCollectingAndLockingUObjectHashTables())   ✗ fatal
```

### 3.2 时间线（同一次崩溃的日志）

| 时刻 | 事件 |
|---|---|
| 10:36:57.3 | `InitialAssemblyLoad`：清单加载 `TheBattleWorld.RuntimeGlue`、`UnrealSharp.Editor`；**`UnrealSharp` 未登记** |
| 10:36:59.918 | `LogUnrealSharpEditor: Project 'TheBattleWorld.RuntimeGlue' loaded for incremental generation.`（线程池续体到达 `BuildProjectDependencyMap`） |
| 10:36:59.924 | 游戏线程：`UWorld::CleanupWorld` + `Compacting FUObjectHashTables` + `MAP CHECKDEP`（GC 锁表窗口） |
| 10:36:59.924 | 线程池：`NewObject<UCSManagedAssembly>` 命中 `checkf` → `appError` → 进程退出 |

**同一毫秒相撞**。

### 3.3 定性

- **违规调用必现**：探针（在唯一的 `NewObject<UCSManagedAssembly>` 之前打印线程/状态/栈）显示**每次开编辑器**都会在线程池上走到该点（`IsInGameThread=false`）。
- **崩溃是竞态**：只有那一刻 GC 正锁着哈希表才 fatal。这解释了"一个月前正常、某天开始频繁崩"——**变的是启动时序**（Roslyn 解析耗时 vs 模板地图 GC 时点），不是代码。
- **触发时机不限于启动**：任何引起 GC 的操作（如放置 Actor）都会重新打开窗口，只要那时池线程上的动作正在建对象；记录中的第二次转储即"首位错误之后的级联"（日志出现 `Error reentered`）。

### 3.4 为什么 C++ 侧不需要"查询是否在 GC 期间"

这是常见的困惑点。UE 的做法不是提供状态位让你每次查询，而是**让业务代码在结构上不处于 GC 期间**：

1. **同线程天然互斥**：GC 是游戏线程上的同步阶段（增量可达性分析 `gc.AllowIncrementalReachability` 默认 0/实验性，`GarbageCollection.cpp:302-308`）；业务代码（`Tick`、事件）也在游戏线程。一条线程不可能同时执行两段代码 ⇒ 普通业务代码结构上不在 GC 期间。
2. **只有被 GC 回调进来的代码才在 GC 期间**：`AddReferencedObjects` / `FReferenceCollector` 回调 / GC 清理回调 / `FGCScopeGuard` 保护范围内的路径。对这些上下文，引擎**逐个 API 写明禁止事项**，而不是让你查状态：
   - `UObjectHash.h:138`：*"…the operation must not modify the UObject hash maps so it can not create, rename or destroy UObjects."*
   - `UObjectGlobals.cpp:536/695/719`：`StaticFindObjectFast`/`StaticFindAllObjects` 在 GC 期间被调用直接 `Fatal`（"Illegal call to … while garbage collecting!"）。
   - `UObjectGlobals.h:343`：需要"GC/存盘期间也能工作"的查询，引擎另给 `…Internal` 变体，文档写明此时返回 `nullptr`。
3. **反向保护是锁而不是查询**：`FGCScopeGuard`（`GarbageCollection.h:116-134`，注释 *"Prevent GC from running in the current scope"*）实现为 `FGCCSyncObject::LockAsync()/UnlockAsync()`（`GarbageCollection.cpp:191-223`）；GC 侧 `AcquireGCLock()` → `GCLock()`（`:4740-4754`）会等待所有 scope guard 释放。真实用例：`WeakObjectPtr.cpp:151/163`、`AsyncLoading2.cpp:11438`、`ReferencerFinder.cpp:238`、`UObjectGlobals.cpp:653/684`。

⇒ `checkf` 的定位是**契约断言（抓 bug）**，期望的失败方式是"写出了结构上不该出现的代码"，而不是"忘了一次 `if`"。C++ 里真正会踩到的只有两类：把建对象逻辑放进 GC 回调；**显式**把业务逻辑放到非游戏线程（`AsyncTask(AnyBackgroundThread…)`、`FRunnable`、task graph worker）。

### 3.5 为什么 C# 侧会破：`async/await` 引入了隐式换线程

C++ 里线程归属由**调用来源**决定，函数不会自己偷偷换线程。C# 的 `async` 相反：`await` 之前的代码在游戏线程，**`await` 之后的续体线程由调度器决定**（默认没有上下文 ⇒ 落在完成任务的池线程上）。于是 C++ 里免费成立的前提——"这段代码是业务代码 ⇒ 由游戏线程调用 ⇒ 不在 GC 期间"——**在 C# 里不再自动成立**。

更关键的是：池线程与"游戏线程上的 GC 阶段"不是互斥，而是**并发**——它不受 GC 约束，只是恰好 GC 锁表那一刻才 fatal。

## 4. 现象与判读

- **日志签名**（按出现顺序）：`Assertion failed: !IsGarbageCollectingAndLockingUObjectHashTables()` → `Unable to create new object: CSManagedAssembly … Creating UObjects while Collecting Garbage is not allowed!` → 托管侧 `TypeInitializationException`（`UCSEditorBlueprintFunctionLibrary` 的静态构造在 fatal 过程中失败）→ `EXCEPTION_ACCESS_VIOLATION`。
- **出现时机**：编辑器启动后十几秒（记录 17.6 s）；或任何触发 GC 的操作（放置 Actor）。
- **误判风险**：断言文本指向引擎 GC，UnrealSharp 的线索只有紧随其后的那行 `Failed to load solution … TypeInitializationException … UCSEditorBlueprintFunctionLibrary`；不看日志的人容易当成"UE 偶发 GC 崩溃"。
- **"看起来没问题"的陷阱**：绝大多数 off-thread 误用没有断言，读一个属性常常"读到正确值"——data race 的特征是**不报错 ≠ 正确**，可能表现为很久以后的内存破坏或随机崩溃。

## 7. 修复（`39959cea`）技术细节

语义是"**要么在游戏线程正确执行，要么失败得可捕获**"，不是"掩盖"。

| 层 | 内容 | 关键点 |
|---|---|---|
| **① 结构层（治本）** | 新增 `Bind_Async::RunOnGameThread(FGCHandleIntPtr)`（`Bind_Async.cpp:37-51`）+ C# `UnrealSharp.GameThreadDispatcher.RunAsync(Action)`；`BuildProjectDependencyMap` 改走它 | 原生侧只在 `IsInGameThread() && !IsGarbageCollecting()` 时 inline，否则 `AsyncTask(ENamedThreads::GameThread, …)` 排队；**不需要 world context**（启动期可用）⇒ 违规动作本身消失 |
| **② 托管调用边界** | 新增 `UnrealSharp.Core.EngineCallGuard`（查询走原生 `Bind_UCSManager.IsOnGameThread/IsCollectingGarbage`）；应用于 `NativeReflectionHelper.GetNativeField` 与 `UObject.NewObject<T>` 的**首条语句**；`GetNativeField` 取到 0 时**抛异常** | 生成绑定的静态构造拿不到指针必须失败，否则后续用空指针调原生会命中 `Bind_UFunction.cpp:8` 的 `check(NativeFunction)` 二次致命 |
| **③ 原生最后一道守卫（拒绝，不排队）** | `CSManager::LoadAssemblyByPath` **顶端**、`Bind_UCoreUObject::GetNativeField`、`Bind_UObject::CreateNewObject`：`!IsInGameThread() \|\| IsGarbageCollecting()` 时记 Error（线程 + GC 状态 + 调用栈）并返回 `nullptr`；`FCSFieldName::ResolveAssembly` 失败返回空指针 | 守卫是**真代码分支，不是 `checkf`** ⇒ Shipping 同样生效 |

**刻意不做"排队重试 + 返回空"**：实测它会继续流过生成绑定触发二次致命；且 .NET 静态构造一旦失败，该类型在本进程内永久不可用。

**验证深度**：A/B 探针（修前 `IsInGameThread=false`、线程 70396/87652 → 修后 `true`，程序集照常加载 + `C# Hot Reload is ready`）；强制 GC（`gc.CollectGarbageEveryFrame=1`）；强制 GC + 改 `.cs` 热重载；两次故障注入（绕开派发 → 得到可捕获异常；只留原生守卫 → 原生拒绝生效且托管判空抛异常被捕获）。

**已知边界**：① 守卫只覆盖已枚举入口（托管 2 处、原生 3 处），`RegisterManagedType_Native`（→ 类型编译器建 `UClass`/`UStruct`）与 `CreateNativeFunctionCustomStructSpecialization`（`NewObject<UFunction>`）无守卫；② dispatcher 缺生命周期协议（`Send` 排队后无限等待、world 失效静默丢回调、未执行任务的句柄归属与关机/取消/ALC 排空未定义）；③ 被拒后该托管类型本进程永久不可用；④ Shipping 下未守卫的违规仍是 UB。

## 8. 后续加固方向（技术口径 0~5）与本 fork 的决策

师傅复核（源码级只读）给出的原顺序：

| 步 | 内容 | 动机 / 关键点 |
|---|---|---|
| 0 | 策略清单 + 现状回归用例 | 建"哪些入口只能游戏线程用"的可审计清单；用例须同时证明"非法被拒且无副作用"与"合法调用有真实效果" |
| 1 | 补齐已确认遗漏入口 + 完善拒绝状态 | `RegisterManagedType_Native` 返回 `void`、`CreateNativeFunctionCustomStructSpecialization` 返回指针 ⇒ 必须有可传播的错误状态，不能只 `return;`/`null` |
| 2 | dispatcher 取消/停机/ALC 归属审计 | 先修丢回调 / `Send` 无限等待 / `PluginLoader.WaitForAllActiveTasks()` + `GetResult()` 与 GT 互等可死锁；明确句柄唯一释放方（已有默认释放，勿重复 `Free`） |
| 3 | 统一策略生成 + 覆盖检查（含直接内存/marshaller） | 由"逐个入口手加"升级为生成器注入 + 原生统一宏；覆盖 marshalling 与直接内存读写 |
| 4 | 整修上下文与 unload 等待后，灰度启用"受控入口作用域上下文" | 让 `await` 续体默认回 GT（save → install → `try/finally` restore），不能直接复用现有 world-bound 实现 |
| 5 | （可选）静态元数据初始化改造 | 把"一次失败永久不可用"改成可失败可重试的状态机 |

**本 fork 的决策（2026-09）**：**放弃第 ④ 步**——帧量化延迟（每次续体等到下一个 tick）、后台重活被搬上 GT、一旦有上下文则"GT 上阻塞等待"变成经典 self-deadlock、对现存项目是行为变更，且它管不到 `Task.Run`/计时器/第三方回调/终结器等**无上下文可捕获**的路径。
**改为**：**Tier A**（建对象/注册类型/加载程序集/解析字段等入口在**所有配置含 Shipping** 始终拒绝）+ **Tier B**（属性读写/marshalling 等热路径在 **Development/Test** 注入检查，响亮失败）+ **分析器**（编译期 `US0015+` 提醒）+ **编码规范**（`docs/C#脚本线程与引擎访问规范.md`）。
具体交付物、复核意见、验证与待决定项见 `解决方案.md`。

## 9. 能保证什么 / 不能保证什么

**能保证**：对纳入契约的 UnrealSharp 引擎访问边界，在所有发布配置下**拒绝**不合法的线程/GC/生命周期调用，并且有测试证明"拒绝无副作用、合法调用结果正确"。
**不能保证**：绕过生成通道的写法——自定义 `Task.Run`、`ConfigureAwait(false)`、计时器、第三方回调、自建线程、`unsafe` 裸函数指针、失效 `UObject` 与跨热重载缓存——插件管不到。纪律仍是：**`await` 之后要碰引擎，必须先回到游戏线程**（`GameThreadDispatcher.RunAsync` / `ConfigureWithUnrealContext()`）。
